# Frontend: проверка в браузере

[Содержание](../../README.md) · [Request ID и серверные тайминги](<../5. Рекоммендации/request-timing.md>)

Проверять под обычным сотрудником с характерными для него правами. Администратор может видеть больше данных и получать другую нагрузку. Выбрать используемые разделы портала; операции записи выполнять на тестовых сделках и задачах: смена стадии может запускать роботов и интеграции.

Для сравнения использовать тот же браузер, компьютер и набор данных. В Network и Performance начать с No throttling. Сделать 3–5 повторов, сравнить медиану и разброс; отдельно проверить [кеш](#кеш-браузера) и [VPN](#сравнение-lan-и-vpn).

## Загрузка страниц и запросы

DevTools → Network: включить Preserve log, очистить список запросов и выполнить один сценарий. Сначала смотреть все запросы, затем Fetch/XHR. Измерять от действия до готовности нужного элемента, а не только до события `Load`.

| Сценарий | Что сделать и когда остановить замер |
| --- | --- |
| Список сделок | Открыть CRM → Сделки в режиме списка. Дождаться строк и возможности открыть сделку |
| Канбан | Переключиться на доску со стадиями. Дождаться карточек и возможности работать с ними |
| Карточка сделки | Открыть из списка в боковой панели (слайдере), затем отдельно по прямой ссылке. Дождаться полей и истории; это разные способы загрузки |
| Фильтр и поиск | Применить сохранённый фильтр, задать новый, сбросить. Проверить поиск по известной сделке и запрос без результатов. Дождаться обновлённого списка |
| Задачи | Открыть свой список, отфильтровать по ответственному/статусу, открыть задачу с комментариями |
| Файлы и документы | В Битрикс24 Диске открыть папку, загрузить тестовый файл, скачать его, открыть превью. Передачу файла и подготовку превью замерять отдельно |
| Чат | Открыть диалог, загрузить историю, отправить тестовое сообщение и проверить появление у второго пользователя |

Для списков сравнить обычную и большую выборку; для карточек — простую и насыщенную полями, связями и историей. Не оценивать весь портал по одной пустой сделке.

| Где смотреть | Что искать |
| --- | --- |
| Timing | Queueing, DNS, Connect/TLS, Waiting (TTFB), Content Download |
| Initiator | Код, запускающий запрос, и зависимые вызовы |
| Waterfall | Последовательные ожидания, повторы, лишний polling |
| Size / Transferred | Большие ответы, JS/CSS/изображения, попадания в кеш |
| Headers / Response | HTTP-код, ошибки в ответе, `Cache-Control`, `Content-Encoding`, Request ID |

Открытие карточки часто вызывает несколько запросов к `/bitrix/services/`, `/bitrix/tools/` и пользовательским обработчикам. Найти тот, без которого интерфейс остаётся заблокирован. Длительности параллельных запросов не складывать.

Долгое Waiting (TTFB): сопоставить запрос с [серверными таймингами](<../5. Рекоммендации/request-timing.md>). Долгое Content Download: проверить размер ответа и сеть. Незавершающийся WebSocket/long polling чата сам по себе не означает зависшую загрузку.

## Реакция интерфейса и JavaScript

DevTools → Performance: начать запись, выполнить одно действие, остановить после появления результата.

Проверить:

- В канбане перетащить тестовую сделку на другую стадию: движение карточки, подтверждение сохранения, обновление доски.
- В карточке открыть вкладки, раскрыть историю, выбрать компанию/контакт, изменить и сохранить поле. Проверить карточку с большим количеством пользовательских полей.
- В списке применить фильтр, отсортировать строки, перейти на следующую страницу и прокрутить большую выборку.
- В задаче открыть комментарии, в чате — историю и поле ввода. Проверить, не запаздывает ли ввод текста.

В Main thread найти задачи дольше 50 мс. Разобрать Scripting, Layout/Paint и стек функций. Если ответ уже пришёл, но список ещё несколько секунд строится или страница не реагирует, исследовать JS и DOM, а не таймауты Nginx.

Сравнить проблемную карточку с простой, большую выборку с небольшой. Это помогает отличить стоимость объёма данных от общей задержки приложения. Проверить также виджеты и пользовательские вкладки, если они добавлены на портале.

## Ошибки во время работы

DevTools → Console: включить Preserve log, очистить журнал перед сценарием. Воспроизвести открытие карточки, сохранение поля, фильтрацию, загрузку файла и отправку сообщения.

Искать исключения, Unhandled Promise Rejection, Failed to fetch, CORS и ошибки загрузки JS-чанков. По стеку и Initiator найти обработчик; в Network проверить ответ связанного запроса. HTTP 200 может содержать прикладную ошибку или HTML страницы входа вместо ожидаемого JSON.

Если данные сохранились, но индикатор загрузки не исчез, проверить ошибку обработки ответа и последующие запросы. Если проблема появилась после обновления портала и исчезает без кеша браузера, проверить совместимость загруженных версий JS и политику кеширования.

## Кеш браузера

Сравнить полную загрузку списка сделок и карточки по прямой ссылке. Повторное открытие слайдера без перезагрузки страницы проверить отдельно: интерфейс может сохранять данные в памяти независимо от HTTP-кеша.

1. В Network включить Disable cache и перезагрузить страницу. Записать время до готовности, объём передачи и длительность JS/CSS-запросов.
2. Снять Disable cache, загрузить ту же страницу для прогрева, затем повторить замер обычной перезагрузкой. Сравнить время и Transferred.
3. Повторить несколько раз в обоих режимах. Для JS/CSS/изображений проверить `memory cache`, `disk cache`, 304 и заголовки кеширования.

304 требует обращения к серверу; memory/disk cache обычно позволяет избежать передачи ресурса по сети. Повторная загрузка неизменённых файлов с полным телом — повод проверить `Cache-Control`, валидаторы и меняющиеся URL ресурсов.

Disable cache действует при открытых DevTools. Это режим без HTTP-кеша браузера, а не холодный запуск всего портала. Он не сбрасывает OPcache, кеш Битрикса, Redis и buffer pool MySQL. Service Worker, если используется, проверить отдельно в Application → Service Workers / Cache Storage. Серверные кеши для этих замеров не очищать.

Если повторная загрузка почти не быстрее, проверить, где осталось время: некешируемый AJAX, обработка на сервере или выполнение JS. После проверки снять Disable cache, чтобы не продолжать обычные замеры с отключённым кешем.

## Сравнение LAN и VPN

Выполнить одинаковые действия через VPN и из локальной сети клиента. По возможности использовать тот же компьютер; иначе учитывать разницу CPU, браузера и расширений. Проверить, что URL, права, данные и обслуживающий backend сопоставимы.

Для каждого сетевого пути сравнить загрузку без HTTP-кеша и после прогрева по инструкции выше. Иначе первый запуск через VPN легко сравнить с уже прогретым запуском в LAN.

| Сценарий | Что сравнить |
| --- | --- |
| Первый вход в список/карточку | DNS, Connect/TLS, загрузку JS/CSS, время до готовности |
| Повторное открытие карточки и фильтрация | Waiting (TTFB) и серверное время тех же AJAX-запросов |
| Большой список или история | Размер ответа и Content Download |
| Скачивание одного тестового файла | Одинаковый размер, время передачи и скорость |
| Чат и уведомления | Установление соединения, переподключения и задержку доставки; при проблемах проверить [Push](<../1. Сервер/1.9. Node.js + Bitrix Push Server.md>) |

Если через VPN растёт в основном передача ресурсов, а время backend остаётся сопоставимым, исследовать сетевой путь. Если растёт и серверное время, проверить нагрузку в момент теста и различия маршрутизации.

Linux-команды с клиентской машины и разрешённого узла в LAN:

```bash
ping -c 20 portal.example.local
mtr -rwzc 30 portal.example.local
curl -sS -o /dev/null \
  -w 'code=%{http_code}\nDNS=%{time_namelookup}s\nConnect=%{time_connect}s\nTLS=%{time_appconnect}s\nTTFB=%{time_starttransfer}s\nTotal=%{time_total}s\n' \
  https://portal.example.local/
```

Времена `curl` накопительные с начала запроса. Проверить HTTP-код и содержимое: редирект на логин не равен авторизованной карточке. Для сравнения использовать тот же endpoint и способ аутентификации, не публикуя cookies/токены.

`curl` не исполняет JS, `ping` не измеряет пропускную способность. Потери только на промежуточном узле `mtr` могут быть ограничением ICMP. Разницу «время браузера минус время Nginx» нельзя целиком приписать VPN: там также очередь браузера и установка соединений.

## Длительная работа и память

Проверить сценарий сотрудника, который не перезагружает вкладку часами:

- Несколько раз открыть и закрыть карточки сделок в слайдере, возвращаясь к одному списку.
- Переключать фильтры, страницы списка и вкладки карточки.
- Открывать задачи и чаты, прокручивать историю, закрывать панели.

В More tools → Performance monitor следить за JS heap, DOM nodes, listeners и CPU. Сначала прогреть интерфейс, затем выполнить 10–20 циклов. Сравнивать состояние в одной точке — например, список после закрытия всех карточек.

В Memory сравнить heap snapshots до и после циклов с учётом сборки мусора. При устойчивом росте проверить detached elements и Retainers: какие ссылки удерживают закрытые панели и обработчики. Один рост heap до сборки мусора ещё не доказывает утечку. Снимки сами могут приостанавливать страницу.

## Дополнительные замеры

Локальный Lighthouse полезен для первоначальной загрузки: тяжёлые ресурсы, неиспользуемый код, блокирующая отрисовка. Проверить, что тестирует авторизованную страницу, а не форму входа. Оценка загрузки не заменяет проверку фильтров, сохранения и слайдеров.

Ориентиры Core Web Vitals для p75 реальных посещений: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1. Несколько ручных прогонов не дают полевую статистику; лабораторный Lighthouse не измеряет полевой INP.

HAR, heap snapshots и записи Performance могут содержать токены и данные CRM; хранить вне публичного репозитория.
