[Содержание](../../README.md) · [Cron и агенты](<../1. Сервер/1.6. Cron.md>)

## Выполнение автоматизации

- В списке бизнес-процессов открыть протокол проблемного экземпляра: длительные действия, повторы, PHP/REST-ошибки, внешние вызовы.
- В CRM проверить роботов стадий сделок, лидов и смарт-процессов: запуск при каждом изменении, каскады обновлений, массовое создание задач, циклы через вебхуки.
- Сопоставить задержку с импортом, обменом с 1С и массовой обработкой сущностей.
- Время конкретного действия сопоставить с PHP и SQL, а не только с временем жизни всего БП.

Ожидание согласования сотрудника или таймера не означает активную нагрузку. Отладчик роботов может выполнять реальные действия: использовать тестовые сущности. Подробный журнал включать для выбранного шаблона на время проверки, затем вернуть прежнюю настройку.

## Таблицы БП

В БД портала:

```sql
SELECT
    TABLE_NAME,
    TABLE_ROWS,
    ROUND((DATA_LENGTH + INDEX_LENGTH) / 1024 / 1024, 2) AS size_mib
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME IN (
      'b_bp_workflow_instance',
      'b_bp_workflow_state',
      'b_bp_task',
      'b_bp_tracking',
      'b_bp_workflow_template'
  )
ORDER BY size_mib DESC;
```

`TABLE_ROWS` у InnoDB приблизителен. Большая таблица журнала не доказывает причину задержки: искать дорогие запросы к ней в [MySQL](<../1. Сервер/1.3. MySQL.md>). Не очищать таблицы БП прямым SQL.

Состояния — `b_bp_workflow_state`, задания — `b_bp_task`, журнал — `b_bp_tracking`. Перед запросами к данным проверить структуру через `SHOW COLUMNS`: состав полей зависит от версии.
