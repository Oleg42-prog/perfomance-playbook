## Источники нагрузки

В разделе для разработчиков открыть статистику REST, если доступна в установленной версии. Найти приложения, вебхуки и методы с высокой частотой и пиками. Сопоставить с замедлением и журналами интеграций.

Проверить параллелизм, размер пачек, пагинацию, retry/backoff и циклы вида «изменение сделки → событие → интеграция → изменение сделки». Для обмена с 1С смотреть также журнал на стороне 1С.

## Access log

Примеры только для Nginx `combined`: URI в `$7`, HTTP-код в `$9`. Подставить фактический файл из конфигурации Nginx. Большие журналы разбирать на копии вне нагруженного узла.

REST-запросы по минутам:

```bash
awk '$7 ~ /^\/rest\// { print substr($4, 2, 17) }' /path/to/access.log \
  | sort | uniq -c | sort -nr | head -20
```

HTTP-коды REST:

```bash
awk '$7 ~ /^\/rest\// { print $9 }' /path/to/access.log \
  | sort | uniq -c | sort -nr
```

Проверить 429, 500, 502/504. HTTP 200 не гарантирует успех: ошибки бывают в JSON-полях `error` и `error_description`, включая результаты отдельных команд `batch`. Не все интеграции ходят через `/rest/`.

## Медленные методы

По таймингам access log сравнить частоту, суммарное время и задержки методов. Для конкретного запроса использовать [Request ID](<../5. Рекоммендации/request-timing.md>), PHP/SQL-профиль. Частые `crm.*.list`, `crm.*.update` и `batch` оценивать по реальной стоимости, не только по названию.

URL входящего вебхука содержит секрет в пути, а не только в query string. Не публиковать исходные строки лога. Численные лимиты облачного REST не переносить на коробочную установку без проверки её настроек.
