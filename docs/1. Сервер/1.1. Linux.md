# Linux: системные ресурсы

[Содержание](../../README.md) · [Порядок проверок](<../5. Рекоммендации/audit-workflow.md>)

Проверять каждый задействованный узел во время замедления: web, БД, кеш, хранилище. Сопоставлять метрики с одной операцией и временем её выполнения. Разовый снимок вне нагрузки не показывает запас в часы пик.

Команды читают состояние. `mpstat`, `iostat`, `pidstat`, `sar` входят в sysstat; если их нет, использовать существующий мониторинг или отдельно согласовать установку.

## ОС и окружение

```bash
date -u '+%Y-%m-%dT%H:%M:%SZ'
hostnamectl
cat /etc/os-release
uname -r
uptime
systemd-detect-virt
timedatectl
systemctl --failed
```

Зафиксировать ОС, ядро, время работы, тип виртуализации и роль узла. Проверить поддержку ОС и совместимость версий с установленным Битрикс24. `systemd-detect-virt` с результатом `none` завершится ненулевым кодом — это не ошибка сервера.

Для сопоставления логов проверить часовой пояс и синхронизацию часов. Перезапуск незадолго до проверки обнуляет часть счётчиков; низкие значения после него не характеризуют предыдущий пик.

## CPU

```bash
lscpu
nproc
vmstat 1 10
mpstat -P ALL 1 10
pidstat -u 1 10
```

`lscpu` показывает модель и топологию, `nproc` — доступные текущему процессу CPU. В ВМ это vCPU, не обязательно выделенные физические ядра. Квота контейнера/службы может быть ниже видимого числа CPU.

| Показатель | Как оценивать |
| --- | --- |
| `vmstat r`, load average | Устойчивая очередь относительно доступных CPU; load включает также задачи в непрерываемом ожидании, не только вычисления |
| `mpstat %usr`, `%sys`, `%idle` | Длительную загрузку и распределение по ядрам; общий CPU 30% не исключает один полностью занятый поток |
| `%steal` | Отнятое гипервизором время vCPU; устойчивый рост — повод проверить хост и лимиты ВМ |
| `%iowait`, `vmstat b` | Ожидание I/O; сопоставить с дисками и процессами, не считать чистой загрузкой CPU |
| `pidstat %CPU` | Какие процессы потребляют CPU именно за интервал; 100% обычно соответствует одному логическому CPU |

Первый CPU/I/O-отчёт `vmstat` и первый отчёт `iostat` обычно относятся ко времени с загрузки ОС. Для текущей нагрузки смотреть следующие интервалы. Значения `%CPU` в `ps` усреднены за время жизни процесса.

## Память и swap

```bash
free -h
swapon --show
grep -E 'MemAvailable|SwapTotal|SwapFree|Slab|SReclaimable|SUnreclaim' /proc/meminfo
ps -eo pid,user,comm,%cpu,rss --sort=-rss | head -20
```

- Смотреть `available`, а не только `free`: файловый кеш может занимать свободную RAM без дефицита памяти.
- По уже запущенному `vmstat` проверить `si` / `so`. Занятый swap без текущего обмена не доказывает проблему; устойчивый swap I/O во время задержек требует разбора.
- RSS в `ps` указан в КиБ и включает общие страницы. Простая сумма RSS процессов завышает потребление; рост памяти отслеживать у тех же процессов во времени.
- Если память уходит не в пользовательские процессы, проверить Slab и невытесняемую часть `SUnreclaim`.

Свободная RAM узла не исключает лимит памяти службы/контейнера или PHP `memory_limit`. OOM искать в журнале ядра ниже.

## Диски и файловые системы

```bash
lsblk -o NAME,TYPE,SIZE,ROTA,FSTYPE,MOUNTPOINT
df -hT
df -i
findmnt -T /home/bitrix/www
findmnt -T /var/lib/mysql
iostat -xz 1 10
pidstat -d 1 10
```

Пути заменить на document root и фактический MySQL `datadir`. Определить, где размещены БД, upload, кеш, временные файлы и логи. `ROTA=0` в ВМ не доказывает, что физическое хранилище — SSD.

| Показатель | Как оценивать |
| --- | --- |
| Свободное место и inode | Заполнение конкретной файловой системы; места может хватать, а inode закончиться |
| `r_await`, `w_await` | Задержки чтения/записи вместе с ожиданием в очереди; сравнить с обычной нагрузкой и характеристиками хранилища |
| `aqu-sz`, IOPS, КиБ/с | Рост очереди при замедлении, достижение лимитов IOPS/пропускной способности диска ВМ |
| `%util` | Сопоставить с задержками; 100% не универсальный предел производительности для NVMe/RAID |
| `pidstat -d` | Какие процессы создают I/O; учитывать буферизацию и отложенную запись |

Для LVM/RAID сопоставить логическое устройство с нижележащими дисками, не складывать один I/O на разных слоях. Для сетевых дисков нужны также метрики сервера хранилища: [файловое хранилище](<../3. Битрикс24/3.4. Файловое хранилище.md>).

`fio`, тесты записи, `drop_caches` и рекурсивный `du` по миллионам файлов не нужны для начальной оценки production.

## Сеть

```bash
ip -br addr
ip route
ip -s link
ss -s
sar -n DEV,EDEV,TCP,ETCP 1 10
```

Определить интерфейсы и маршруты между web, БД, Redis и хранилищем. В `sar` смотреть трафик, ошибки интерфейса и `retrans/s`; в `ip -s link` сравнить прирост errors/dropped между снимками. Счётчики узла не показывают, какой именно запрос пострадал.

Скорость и состояние физического интерфейса, если доступны; `eth0` заменить на своё имя:

```bash
ethtool eth0
```

В виртуальной среде заявленная скорость интерфейса не равна гарантированной пропускной способности. Задержки и потери между узлами сопоставлять со временем SQL/API. Пользовательский путь и влияние VPN проверять отдельно: [Frontend](<../2. Браузер/2.1. Frontend.md#сравнение-lan-и-vpn>).

## Лимиты служб и контейнеров

Для фактически используемой службы; пример PHP-FPM:

```bash
systemctl show php-fpm \
  -p ControlGroup -p CPUQuotaPerSecUSec -p MemoryMax \
  -p TasksMax -p LimitNOFILE
```

Проверить квоты CPU/RAM, лимит задач и дескрипторов. Для контейнера нужны также ограничения runtime и cgroup. Узел может иметь свободные ресурсы, а конкретная служба — достигать своего лимита. Снижение лимитов и их автоматическое увеличение в диагностику не входят.

## Ошибки ядра

```bash
sudo journalctl -k --since '24 hours ago' --no-pager \
  | grep -Ei 'oom|out of memory|killed process|i/o error|read-only|reset|hung task'
```

При OOM найти пострадавший процесс и различить нехватку памяти узла и лимит cgroup. При I/O error, reset устройства или read-only проверить хранилище до тюнинга приложения. Отсутствие совпадений не исключает ошибок, если журнал недоступен или нужный период не сохранился.

Для [отчёта](<../6. Отчет/report-template.md#2-серверные-ресурсы-и-нагрузка>) сохранить характеристики каждого узла и интервальные метрики с временными отметками. Отдельно указать, измерялся ли рабочий пик и какое ограничение действительно наблюдалось; число пользователей само по себе не задаёт норму CPU/RAM.
