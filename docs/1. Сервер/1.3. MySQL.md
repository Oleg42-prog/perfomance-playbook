# MySQL / Percona

[Содержание](../../README.md) · [Linux](<1.1. Linux.md>)

SQL ниже выполнять в консоли `mysql` на нужном экземпляре БД. Для полного processlist и InnoDB Status нужен `PROCESS`, для `performance_schema` и `sys` — права чтения. Примеры для MySQL 5.7/8.x и совместимых Percona Server.

## Версия и логи

```sql
SELECT @@hostname, @@port, VERSION(), @@version_comment;

SHOW GLOBAL VARIABLES WHERE Variable_name IN (
    'datadir', 'log_error', 'slow_query_log',
    'slow_query_log_file', 'long_query_time', 'log_output'
);
```

Журнал службы или конец файла из `log_error`:

```bash
sudo journalctl -u mysqld -u mysql --since '24 hours ago' --no-pager
sudo tail -n 200 /path/to/mysql-error.log
```

Искать `Too many connections`, ошибки InnoDB, OOM, нехватку места, перезапуски. Deadlock и lock timeout искать также в PHP-логах: не все ошибки SQL попадают в error log.

## Конфигурация

```sql
SHOW GLOBAL VARIABLES WHERE Variable_name IN (
    'innodb_buffer_pool_size',
    'innodb_redo_log_capacity',
    'innodb_log_file_size',
    'innodb_log_files_in_group',
    'innodb_flush_method',
    'innodb_flush_log_at_trx_commit',
    'sync_binlog',
    'max_connections',
    'tmp_table_size',
    'max_heap_table_size',
    'table_open_cache',
    'performance_schema'
);
```

- Buffer pool: размер в байтах; сравнить с RAM, другими службами и физическими чтениями.
- Redo: `innodb_redo_log_capacity` в MySQL 8.0.30+, в старых версиях размер задают `innodb_log_file_size × innodb_log_files_in_group`. Отсутствующие переменные не выводятся.
- `max_connections`: сравнить с текущими подключениями и пиком. Поднятие лимита увеличивает потенциальный расход памяти.
- Временные таблицы: учитывать версию и движок; `tmp_table_size` и `max_heap_table_size` не описывают все лимиты TempTable в MySQL 8.
- `innodb_flush_log_at_trx_commit` и `sync_binlog` влияют на сохранность данных при сбое.

## Нагрузка

Снять два раза с интервалом около 60 секунд во время замедления:

```sql
SELECT UTC_TIMESTAMP() AS captured_at_utc;

SHOW GLOBAL STATUS WHERE Variable_name IN (
    'Uptime',
    'Threads_connected',
    'Threads_running',
    'Max_used_connections',
    'Aborted_connects',
    'Slow_queries',
    'Created_tmp_tables',
    'Created_tmp_disk_tables',
    'Innodb_buffer_pool_reads',
    'Innodb_buffer_pool_read_requests',
    'Innodb_row_lock_waits',
    'Innodb_log_waits'
);
```

| Метрика | Что смотреть |
| --- | --- |
| `Threads_connected`, `Threads_running` | Текущее число подключений и работающих потоков |
| `Max_used_connections` | Исторический пик подключений после запуска/сброса |
| `Innodb_buffer_pool_reads` | Прирост физических чтений относительно логических `read_requests`; сравнить с I/O узла |
| `Innodb_row_lock_waits` | Новые ожидания блокировок |
| `Innodb_log_waits` | Ожидания освобождения log buffer; проверить запись redo и диски |
| `Created_tmp_disk_tables` | Прирост дисковых временных таблиц; не учитывает все варианты сброса TempTable в MySQL 8 |

Для накопительных счётчиков считать `Δзначения / Δсекунд`. При перезапуске или сбросе статистики снять заново. `Threads_*` — текущие значения, не счётчики. `Slow_queries` зависит от порога `long_query_time`.

CPU, память и диски смотреть одновременно: [команды Linux](<1.1. Linux.md>).

## Запросы

Текущие сессии:

```sql
SHOW FULL PROCESSLIST;
```

Смотреть `Time`, `State`, повторяющиеся SQL. `Sleep` не означает медленный запрос, но сессия может удерживать транзакцию.

Топ по суммарному времени, если включён сбор Performance Schema:

```sql
SELECT
    SCHEMA_NAME,
    DIGEST,
    LEFT(DIGEST_TEXT, 300) AS query_pattern,
    COUNT_STAR AS executions,
    ROUND(SUM_TIMER_WAIT / 1e12, 3) AS total_s,
    ROUND(AVG_TIMER_WAIT / 1e9, 3) AS avg_ms,
    SUM_ROWS_EXAMINED AS rows_examined
FROM performance_schema.events_statements_summary_by_digest
WHERE DIGEST IS NOT NULL
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;
```

Данные по всем схемам, накоплены с начала сбора/сброса. Для конкретного интервала сравнивать снимки по `SCHEMA_NAME` + `DIGEST`. `total_s` — сумма длительностей, не CPU-время. Пустой список может означать отключённый сбор.

Для включённого slow log с `log_output = FILE` (или `FILE,TABLE`) разобрать копию файла:

```bash
mysqldumpslow -l -s t -t 20 /path/to/slow-log-copy.log
```

`-s t` — суммарное время, `-l` — не вычитать время блокировок. `-t 20` ограничивает вывод, но файл читается целиком; большие логи разбирать вне нагруженного узла.

Для найденных SQL проверить частоту, просмотренные строки, план и источник вызовов: [PHP](<1.4. PHP.md>), [монитор производительности](<../3. Битрикс24/3.1. Монитор производительности.md>), [REST](<../3. Битрикс24/3.3. REST API и интеграции Битрикс24.md>). `EXPLAIN ANALYZE` выполняет запрос.

## Блокировки

```sql
SHOW ENGINE INNODB STATUS\G
```

Секции `TRANSACTIONS` и `LATEST DETECTED DEADLOCK`. Проверить дату deadlock: он может быть старым.

Текущие ожидания InnoDB, если доступна схема `sys`:

```sql
SELECT
    wait_started,
    wait_age_secs,
    waiting_pid,
    waiting_query,
    blocking_pid,
    blocking_query
FROM sys.innodb_lock_waits
ORDER BY wait_age_secs DESC
LIMIT 20;
```

Старые активные транзакции:

```sql
SELECT
    trx_id,
    trx_state,
    trx_started,
    trx_mysql_thread_id,
    trx_rows_locked,
    trx_rows_modified,
    trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started
LIMIT 20;
```

`trx_mysql_thread_id` соответствует ID в processlist. У бездействующей блокирующей сессии `blocking_query` может быть `NULL`. Возраст транзакции не равен времени блокировки.
