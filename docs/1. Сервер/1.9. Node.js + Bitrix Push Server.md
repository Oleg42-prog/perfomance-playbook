# Push Server

[Содержание](../../README.md)

В настройках модуля Push and Pull проверить, используется локальный или облачный сервер очередей. Команды ниже для локального.

## Процессы, конфигурация, логи

```bash
systemctl list-units --type=service --all | grep -Ei 'push|node'
systemctl status push-server
sudo systemctl cat push-server
sudo systemctl show push-server -p LimitNOFILE -p MemoryMax -p TasksMax -p NRestarts
ps -C node -o pid,ppid,%cpu,%mem,rss,etime,cmd --sort=-rss
sudo ls -lah /etc/push-server/ /var/log/push-server/
sudo journalctl -u push-server --since '24 hours ago' --no-pager
```

В файловых журналах искать ошибки Redis, OOM, аварийные завершения Node.js и переподключения. Пути и имена файлов зависят от версии.

Сверить адрес Redis, pub/sub endpoints, число процессов и ключ с настройками модуля. Версию Node проверять для бинарника из `ExecStart`, не только `node` из PATH. Конфигурация содержит секреты.

## Соединения и доставка

```bash
sudo ss -lntp | grep -E 'node|push'
sudo ss -tanp | grep 'node'
pidstat -C node 1 10
```

- В DevTools → Network проверить соединения WebSocket / long polling, ошибки и частые переподключения.
- В Nginx проверить маршруты публикации/подписки, проксирование WebSocket и 502/504.
- Сопоставить рост `CLOSE-WAIT`, падение числа соединений и рестарты с жалобами пользователей.
- Отправить тестовое сообщение между двумя пользователями, проверить задержку у получателя. Для численной оценки по часам разных машин нужна синхронизация времени.

Проверить именно тот [экземпляр Redis](<1.8. Redis and Memcached.md>), который указан у Push, а не кеш портала. CPU/RAM узла: [Linux](<1.1. Linux.md>).
