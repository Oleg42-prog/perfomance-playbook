# Мониторинг

[Содержание](../../README.md) · [Request ID и тайминги](<../5. Рекоммендации/request-timing.md>)

Если у клиента уже есть Zabbix или Prometheus, добавить недостающие метрики туда. Для нового развёртывания: Zabbix с шаблонами либо Prometheus + exporters + Grafana. Grafana визуализирует данные, но сама не заменяет их сбор.

## Что собирать

| Компонент | Метрики |
| --- | --- |
| Linux | CPU, доступная RAM, swap I/O, место/inode, дисковые задержки и очередь, сеть |
| HTTP | RPS, 4xx/5xx, длительность и p95/p99, доступность из сети пользователей |
| Apache / FPM | Занятые воркеры, очередь, достижения лимитов, slow requests |
| PHP / OPcache | Длительность, ошибки, память, заполнение и рестарты кеша |
| MySQL | Запросы, running threads, подключения, блокировки, физические чтения, redo waits |
| Redis / Memcached | Память, вытеснения, hit/miss, отказы подключений |
| Cron / агенты | Завершение и длительность заданий, возраст последнего успеха, старейший просроченный агент |
| Прикладные очереди | Размер и возраст старейшего задания/почтового события |
| Push / поиск | Рестарты, ошибки, соединения, задержки доставки/поиска |

У `stub_status` Nginx нет распределения кодов и длительностей. Для них нужен разбор access log или инструментирование. SQL/очереди не опрашивать тяжёлыми `COUNT(*)` с частотой scrape без оценки стоимости.

## Prometheus

Linux — node_exporter, MySQL — mysqld_exporter, HTTP-проверки — blackbox_exporter. Для остальных сервисов выбрать exporter, совместимый с версией и нужными метриками. Endpoint-ы закрыть от пользовательских сетей; для БД использовать отдельную учётную запись мониторинга.

Примеры PromQL для стандартных метрик этих exporters.

CPU без idle, % по узлам:

```promql
100 * (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])))
```

Неуспешные blackbox-пробы:

```promql
probe_success == 0
```

Начальные параметры: scrape 15–30 с, хранение 30 дней — с проверкой объёма и нагрузки. Алерты: недоступность, 5xx, длительность операций, OOM/место, насыщение воркеров, блокировки и растущий возраст очереди. Пороги и выдержку подбирать по рабочему профилю, не по разовым пикам.

Метрики размечать ограниченным набором labels: узел, сервис, нормализованный маршрут. Не добавлять Request ID, ID сделки/пользователя или полный URL.

## Логи

Loki + Alloy либо существующий сборщик. По времени и Request ID связать access log, Apache и PHP. Request ID в Loki хранить в содержимом или structured metadata, не как индексируемый label. Токены вебхуков, cookies и персональные данные маскировать до отправки.

HTTP-пробы выполнять из LAN, для удалённых пользователей — также через их сетевой путь. Мониторинг внутри инфраструктуры клиента не должен зависеть от VPN-сессии аудитора.

## Трассировка

OpenTelemetry + Tempo: spans для PHP, SQL, внешних HTTP-вызовов и выбранных обработчиков. Сначала проверить одну операцию на совместимость PHP/SAPI и библиотеки БД, полноту spans и накладные расходы; настроить sampling.

Request ID для поиска в логах не заменяет Trace ID. Для распределённой трассы нужны контекст (`traceparent`) между сервисами и Trace ID в логах. Внутренний код Битрикса может требовать ручного инструментирования.

Для всей пользовательской операции нужны также браузерные измерения. Серверная трасса не выделит VPN и отрисовку JS. Server-Timing показывает метрики в DevTools, но не отправляет их в Prometheus.
